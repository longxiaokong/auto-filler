# 技术方案

## 技术栈

| 层级 | 选型 | 理由 |
|------|------|------|
| 语言 | TypeScript | 类型安全；AI 编程工具生成代码的正确率更高 |
| 插件框架 | WXT | 约定式开发；自动生成 manifest.json；内置 HMR |
| UI | 原生 HTML + CSS + TS | Popup 和设置页逻辑简单，不需要引入 Vue/React |
| PDF 生成 | jsPDF | 纯前端拼装 PDF，无后端依赖 |
| LLM | OpenAI 兼容 API | 语义字段匹配；兼容任何 OpenAI 格式端点（OpenAI / DeepSeek / Ollama / VLM 等） |

## 项目结构

```
auto-filler-extension/
├── wxt.config.ts          # WXT 配置（权限、manifest 覆盖）
├── entrypoints/
│   ├── background.ts      # Service Worker：扫描调度、LLM 匹配、消息路由
│   ├── content.ts         # 注入网页：DOM 扫描、字段填充
│   ├── popup/             # 点击图标弹出的面板（纯 UI 层）
│   │   ├── index.html
│   │   └── main.ts
│   └── options/           # 设置页：用户信息录入 + API 配置 + 导入导出
│       ├── index.html
│       └── main.ts
├── utils/
│   ├── matcher.ts         # LLM 语义匹配（OpenAI 兼容 API）
│   ├── filler.ts          # DOM 字段填充执行
│   └── storage.ts         # chrome.storage 封装
└── assets/
    └── icons/
```

## 核心流程

1. 用户在设置页录入个人信息 + API 配置（Base URL / Key / Model）→ 存入 `chrome.storage.local`
2. 用户打开任意报名/申请页面
3. Content script 扫描页面所有 `<input>`、`<select>`、`<textarea>` 元素
4. 提取每个字段的语义线索：label 文本、placeholder、name 属性、aria-label
5. Popup 发送扫描指令 → Background Service Worker 调用 LLM API 做语义匹配 → 返回字段映射
6. 用户在 Popup 中确认 → content script 填充所有匹配字段

### 架构决策

#### LLM 接入：OpenAI 兼容 API

采用 OpenAI 兼容的 `/v1/chat/completions` 接口，用户在 Options 设置页自行配置：
- **API Base URL**（默认 `https://api.openai.com/v1`，可改为任何兼容端点）
- **API Key**
- **Model 名称**

这样无论接 OpenAI、DeepSeek、本地 Ollama、还是 VLM（截图识别），都一套 API 走通。匹配任务用小模型即可（gpt-4o-mini 级别），成本极低。

#### 数据存储：chrome.storage.local + 导入导出 + 云同步

- **P0**：`chrome.storage.local` 存储所有数据（profile、API 配置）
- **P0**：Options 页提供 JSON 导入/导出按钮，用户可随时备份和恢复
- **P2**：支持上传到云盘同步（如 WebDAV / 网盘 API），参考已有插件的实现方式

不采用 File System Access API 做本地文件夹实时同步（每次需用户手动授权，扩展内支持受限，体验不流畅）。

#### Popup / Background 职责分离

- **Background Service Worker**：执行扫描、LLM 匹配等耗时操作。即使 Popup 关闭，任务不中断
- **Popup**：纯 UI 展示层，通过 `chrome.runtime.sendMessage` 与 Background 通信，不直接调用 LLM API

#### Content Script 注入

采用 WXT 声明式注入（`content_scripts` in manifest），匹配 `<all_urls>`，按需注入。不使用 `chrome.scripting` 动态注入，声明式更简单可靠。

#### 未配置时的降级

Options 页未录入个人信息时，Popup 扫描按钮 disabled，提示「请先在设置页录入个人信息」。未配置 API Key 时同理。

## 用户信息模型

采用**通用字段 + 身份扩展字段**两级结构。设置页顶部提供身份类型下拉框，选择后展开对应扩展字段。

**通用字段**（始终显示）：姓名、性别、身份证号、手机号、邮箱、地址

**扩展字段**（按身份类型显示）：

- 学生：学校、专业、学号、学历、绩点、入学年份
- 公务员：工号、所在部门、职务、职级（MVP 可留空模板）

**存储结构**：

```ts
{
  profileType: 'student',  // 'general' | 'student' | 'civil_servant'
  fields: {
    name: '张三',
    gender: '男',
    // ...通用 + 当前身份的字段
  }
}
```

**匹配策略**：LLM 语义匹配时只发送通用字段 + 当前选中身份的扩展字段。不做全量发送，原因：
- 用户同一时刻只有一种身份，全量发送会引入无关字段
- 字段过多会降低 LLM 匹配准确率（如"学号"与"工号"可能混淆）
- 节省 token

**可扩展性**：新增身份类型只需在配置数组中添加一项字段定义，无需改动 UI 逻辑。

## 功能优先级

### P0（MVP — demo 必须有）

- 设置页用户信息录入（姓名、身份证、手机、邮箱、学校、专业、学历等）
- 页面表单字段扫描（content script）
- LLM 语义匹配 — 核心差异化功能
- 一键填充 + 用户确认
- Popup 默认展示「扫描当前页面」按钮，用户主动点击后才触发扫描和 LLM 匹配（节省 token，避免每次打开 popup 都请求 API）。扫描完成后切换为结果展示 + 确认填充态

### P1（我觉得会做的）

- Popup 面板显示识别到的字段和匹配结果
- 多套信息模板切换 — Popup 顶部身份 Badge 改为微型 select 下拉框，直接在 Popup 里切换身份，无需跳转设置页
- JSON 导入/导出 — Options 页提供导出和导入按钮，备份恢复用户配置

### P2（可能会做的）

- 匹配过程加载动画
- 匹配历史记录
- 云盘同步 — 支持上传到云盘（WebDAV / 网盘 API），参考已有插件实现
- 设置页图片上传 + 拖拽排序
- jsPDF 基础 PDF 拼装（Popup 底部做跳转链接，在新 Tab 打开 options.html#pdf 专门页面处理）

## 关键 Chrome API

- `chrome.storage.local` — 持久化存储用户数据和 API 配置
- `chrome.tabs` — 与当前标签页通信
- `chrome.runtime.sendMessage` — Popup / Background / Content Script 间消息传递
